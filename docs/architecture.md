# Architecture

![CAPY runtime architecture. The Telegram worker handles text and audio, then runs the LangGraph workflow. Gemma transcribes and interprets messages, Laya proposes an action, and Python services enforce booking rules. Redis stores conversation state. PostgreSQL stores bookings, Telegram receipts and demo reminders.](assets/architecture.svg)

Telegram is the customer interface. `app/telegram_worker.py` validates private-chat sender identity, provisions the scoped customer, handles text/audio and saves replies in the durable update ledger.

`app/llm/gemma.py` rewrites a message in simple language and extracts booking facts for Python, without assigning an intent or next action. It also transcribes full recordings. `app/channels/audio_chunks.py` splits decoded audio near pauses with overlap and enforces size/time budgets. No chunk can execute a booking. The completed transcript enters the same interpreter as typed text.

`app/runtime.py` constructs Gemma and Laya directly through the same provider constructors used by evaluations. The normal app rejects deterministic overrides. Provider errors propagate to a safe retry response before writes. `app/graph/laya.py` sends only Gemma's interpreted `message` and draft `context` to Laya. Laya proposes the action; Python enforces required facts, valid references and booking authorization. External servers must follow the [model contracts](model-contracts.md).

`app/graph/workflow.py` invokes one graph turn with a stable business/bot/user thread. Its Redis checkpoint owns draft, offered slots and at most 24 history messages. There is no separate draft/history/slot store. Private booking results stay in request-scoped `CustomerSchedulingActions`, outside checkpoints. `lg:v3` isolates the interpreted-message contract from older temporary state.

`app/graph/actions.py` defines `SchedulingActions`, the protocol for operations the workflow may request. `CustomerSchedulingActions` in `app/customer_scheduling_actions.py` implements that contract for the trusted business/customer identity and calls deterministic services. Evaluation fixtures implement the same contract without real booking writes. `app/booking.py` checks ownership and current policy inside transactions; `app/scheduling.py` handles local time, service assignment, notice, horizon, buffers and conflicts. PostgreSQL's exclusion constraint independently prevents overlaps. The business-row lock deliberately serializes writes per business for a simple idempotency boundary; this limits throughput and should be measured before changing.

`app/channels/telegram_repository.py` owns identity provisioning, update receipts, polling offsets and saved replies. Phone data never chooses the customer record. Duplicate updates do not rerun a turn; a crash with an unknown committed outcome yields a check-your-appointments response. Saved replies retry without rerunning booking operations. External reply delivery can duplicate after an ambiguous send timeout.

`app/reminders.py` writes demo reminders into an inbox using `SKIP LOCKED` and bounded retry. It has no graph dependency. `app/cli.py` is a local owner inspection command that constructs only a PostgreSQL repository. `app/main.py` exposes health only and constructs its own Redis client. Neither entry point constructs Gemma, Laya or the conversation graph; only the Telegram worker needs the full application runtime.

See the [database guide](database.md) for table relationships and reminder delivery.

`app/evals/` runs the real workflow with synthetic service boundaries or isolates extraction/routing. It does not establish database correctness: PostgreSQL/Redis integration tests cover that separately. The local model server implements both inference contracts. Training is future work.

## How the Telegram worker works

The Telegram profile runs `python -m app.telegram_worker` as a separate process. The worker listens for Telegram updates, establishes who the sender is, and delivers replies. PostgreSQL tracks update receipts, the polling position and saved replies. LangGraph uses Redis to retain the conversation between turns. [Compose worker · L78–94](../docker-compose.yml#L78-L94) · [`main()` · L344](../app/telegram_worker.py#L344) · [Redis checkpoint setup · L59](../app/runtime.py#L59)

### Terms used in this flow

| Term | Meaning in CAPY |
| --- | --- |
| **Update** | An event Telegram gives the bot, such as a customer message. Each update has a numeric `update_id`. |
| **Polling** | The worker repeatedly calls Telegram’s `getUpdates` method to ask for available updates. The call can wait for a configured period for new messages. |
| **Offset** | The next update ID CAPY asks Telegram to return when polling. For example, after CAPY saves update `100`, it records `101` as the next offset and uses that value on a later `getUpdates` call. Telegram can then confirm earlier updates as received. The offset tracks intake, so update `100` may still be waiting for processing or reply delivery. CAPY saves the update and next offset together in PostgreSQL, then advances its in-memory offset. After a restart, it reads the saved offset and continues polling. [`save_update()` · L41](../app/channels/telegram_repository.py#L41) · [`_poll_updates()` · L67](../app/telegram_worker.py#L67) |
| **Webhook** | A URL Telegram can call to deliver updates to an application. CAPY checks for an existing webhook before starting its polling worker. |
| **Receipt** | CAPY’s PostgreSQL record of a Telegram update. Its status records progress from `received` to `processing`, then `reply_ready` and `delivered`. Ignored updates can move from processing directly to delivered. The `(bot_id, update_id)` key identifies a receipt. |
| **Claim** | Changing a received receipt to `processing` before the worker handles it. The update is claimed only if it is still in the `received` state. |
| **Advisory lock** | A PostgreSQL lock that cooperating worker processes use to coordinate. CAPY holds one per bot while its polling worker runs. |
| **Turn** | One scheduling message processed through LangGraph. A voice recording is fully transcribed before it enters one turn. |
| **Checkpoint** | Temporary conversation state saved in Redis, including the draft and offered slots, so a later turn can continue the same conversation. |
| **Idempotency key** | A stable value derived from the bot and update IDs. Booking services use it with a request hash to recognize a repeated write and reuse its saved outcome. |
| **Payload** | The update data saved in the receipt while it is being processed. CAPY clears it when it saves the reply or marks the update ignored. |

### Input and error paths

- **Commands and contact cards.** The worker handles `/start` with a welcome message. It updates the linked customer’s optional phone number when the sender shares their own Telegram contact card. The identity link continues to determine access to bookings. [`_reply_to_message()` · L133](../app/telegram_worker.py#L133) · [`_contact_reply()` · L177](../app/telegram_worker.py#L177)
- **Text and audio.** Text goes straight to the scheduling turn. A voice note or audio attachment is downloaded within the configured size limit and transcribed in full first. Waiting for the complete recording lets the workflow account for a correction near the end before attempting a booking. [`_message_input()` · L190](../app/telegram_worker.py#L190) · [`get_file()` · L104](../app/channels/telegram.py#L104) · [`transcribe_recording()` · L38](../app/llm/gemma.py#L38)
- **Failed turns.** A language provider failure asks the customer to retry and reports that the booking was unchanged. A booking rule violation returns its domain message, such as asking for a different slot. An unexpected failure can occur after a write commits, so the worker asks the customer to check their appointments before trying again. [Turn error handling · L153–175](../app/telegram_worker.py#L153-L175)
